# Unit 5.11 — Research Software Engineering for Environmental Data Science

**Status:** Draft  
**Estimated effort:** 7 hours  
**Audience:** Environmental and geospatial analysts moving from notebooks and one-off scripts to maintainable research software  
**Prerequisites:** Python fundamentals, a small analysis project, and basic command-line/file-system literacy

## Purpose

Scientific results are only as dependable as the workflow that produces them. This unit develops a practical engineering discipline for environmental analysis: version control, small testable functions, dependency and environment management, data contracts, documentation, packaging, continuous integration and reproducible releases. The objective is not to turn every research notebook into a large software product; it is to make important analyses understandable, testable, rerunnable and reviewable.

## Learning outcomes

Learners will be able to:

1. Use Git branches, focused commits, diffs and pull requests to make scientific changes traceable.
2. Refactor repeated analysis logic into small functions with explicit inputs, outputs and failure behaviour.
3. Design unit, integration, property-based and regression tests for scientific data transformations and numerical invariants.
4. Pin and document software environments, separate configuration from code, and make data provenance and licensing explicit.
5. Build documentation, automated checks and a reproducible release record that communicates limitations and known failures.

## Lesson 5.11.1 — Version control as research provenance

A Git repository records changes to code and documentation, not the truth of a scientific conclusion. Use a meaningful branch for a bounded change, inspect diffs before committing, and keep commits coherent enough to review. Record the reason for a methodological change, not only the file that changed. Avoid committing credentials, private records, large derived data without policy, or unlicensed source data.

**Practice:** Create a repository for a small environmental analysis. Add a README, environment specification and data-source note; make a feature branch; change one analysis function; inspect the diff; commit; and open a reviewable pull request.

## Lesson 5.11.2 — Modular design and data contracts

A maintainable pipeline separates ingestion, validation, transformation, analysis and presentation. Functions should have explicit contracts: expected column names and types, units, coordinate reference system, time convention, missing-value rules and output shape. Validate assumptions at boundaries and fail with actionable messages rather than silently coercing scientifically meaningful values.

**Environmental case:** A raster stack and station table can look numerically compatible while differing in CRS, pixel alignment, units or time zone. Encode these checks as contracts before joining or modelling.

**Practice:** Refactor one notebook workflow into pure or mostly pure functions. Write a data contract for the input and assert it before processing. Keep file paths and credentials out of hard-coded source.

## Lesson 5.11.3 — Scientific testing: beyond “the script ran”

Use unit tests for small transformations, integration tests for connected pipeline stages, and regression tests for previously identified failures. Property-based tests can check invariants across generated inputs; numerical tests should use justified tolerances rather than exact floating-point equality. Test scientific invariants such as conservation under a valid transformation, monotonicity where mathematically expected, coordinate bounds, uniqueness and dimensional consistency.

A test passing means the tested property held for the tested cases; it does not validate the full conceptual model, source-data quality or causal interpretation. Include edge cases: missing timestamps, duplicated keys, empty subsets, all-NA groups, unexpected CRS and extreme values.

**Practice:** Write tests for a unit conversion, a time-index validator and a raster/table join. Include at least one intentionally failing case and show that the error is informative.

## Lesson 5.11.4 — Environments, dependencies and reproducibility

Record the supported language/runtime version and direct dependencies, use a lockfile or sufficiently pinned environment where appropriate, and document installation and execution steps from a clean environment. Separate configuration from code, use environment variables or a secrets manager for credentials, and do not assume that a notebook kernel matches the deployment interpreter.

Reproducibility also depends on data versions, source URLs, licences, checksums or immutable identifiers where available, random seeds, spatial/temporal conventions and external services. A seed alone does not guarantee identical results across library versions, hardware or nondeterministic algorithms.

**Practice:** Recreate the analysis in a clean environment. Record dependency installation, data acquisition, expected outputs and known non-determinism. Confirm that a colleague could follow the README without undocumented manual steps.

## Lesson 5.11.5 — Documentation, CI and scientific releases

Automated checks can run formatting, lint, unit tests, type checks, data validators and a build on each pull request. Keep fast checks fast, make failure messages actionable, and do not weaken tests merely to obtain a green badge. A release note should name the analysis version, data provenance, method changes, validation evidence, limitations and known issues.

Documentation should distinguish supported public functions from internal implementation details and include a minimal example. CI verifies the configured checks in its execution environment; it does not certify scientific validity or prove that an analysis is appropriate for every dataset.

**Practice:** Configure a lightweight CI workflow to run tests and validation. Create a release checklist that requires a clean rerun, source/licence records, test evidence and a limitations section.

## Deliverables

1. A version-controlled environmental analysis repository with a coherent commit history.
2. A module and data-contract design note.
3. A scientific testing suite with edge cases and numerical invariants.
4. An environment and reproducibility record.
5. A release-ready README, CI checks and scientific release note.

Before release, run the examples in a clean environment, review test assertions for meaningful scientific invariants, verify documentation links, and inspect the rendered lesson routes. Keep the unit in **draft** until those gates pass.
