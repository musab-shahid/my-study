# Unit 5.5 — Data workflow and engineering basics · Core

**Tag:** Core  
**Outcome:** Design raw→interim→processed workflows; use SQL for structured extracts; acquire data via APIs with logging; maintain manifests; keep secrets out of git.

**Prerequisites:** 5.2.  
**Builds toward:** 5.11–5.12; Subjects 2–4 data practice.

### Learning outcomes (L3)
1. Implement an immutable-raw workflow with clear stage boundaries.
2. Write and test SQL joins/aggregations against known row counts.
3. Acquire data from an API or bulk download with retries, cache, and logged parameters.
4. Produce a dataset manifest (source, version, access date, licence, units, checksum).
5. Store credentials outside the repository.

---

## 5.5.1 End-to-end scientific workflows

### 5.5.1.1 Stages
1. **Acquire** — download/extract with logged parameters.  
2. **Validate** — schema, ranges, CRS, time zone, completeness.  
3. **Transform** — clean, join, aggregate; write interim products.  
4. **Analyse** — statistics/models on processed inputs only.  
5. **Publish** — tables/figures/package; never overwrite raw.

### 5.5.1.2 Idempotence
Re-running a stage with the same inputs yields the same outputs. Avoid “append forever” without deduplication keys.

### 5.5.1.3 Minimum manifest
```yaml
dataset_id: era5_t2m_multan_2015_2024
source: CDS ERA5 single levels
variable: 2m_temperature
units: K
spatial: "bbox [...]."
temporal: 2015-01-01/2024-12-31
access_date: 2026-03-15
licence: "Copernicus — verify current terms"
request: {product_type: reanalysis, ...}
checksum_sha256: "..."
notes: "Daily max on PKT local days"
```

## 5.5.2 SQL and structured data

### 5.5.2.1 Relational ideas
Separate **station metadata** from **observation time series**. Primary keys, foreign keys, one-to-many relationships.

### 5.5.2.2 Core SQL
`SELECT`, `WHERE`, `JOIN`, `GROUP BY`, `ORDER BY`; window functions at a working level. Always check counts before/after joins.

### 5.5.2.3 Tools
SQLite for local projects; PostgreSQL/PostGIS when multi-user or spatial SQL is needed (Subject 3). Pandas `read_sql` for analysis extracts.

**Practice A2.** Given tables `stations(id, name)` and `daily(station_id, date, tmax)`, write SQL for mean June tmax by station for one year; state how you would verify the result.

## 5.5.3 APIs and acquisition

### 5.5.3.1 HTTP hygiene
Status codes, pagination, rate limits. Exponential backoff on 429/5xx.

### 5.5.3.2 Climate/EO endpoints
CDS, Earthdata, agency portals: pin client library versions; save the exact request payload; cite the dataset. Platform migrations break unpinned clients (Unit 2.5).

### 5.5.3.3 Local cache
Store downloads under `data/raw/` with manifest entries so analyses survive upstream path changes.

---

## 5.5.4 Provenance, licensing, credentials

### 5.5.4.1 Licence compliance
Attribution, share-alike, non-commercial clauses; derived-data rules. Do not redistribute restricted station data.

### 5.5.4.2 Secrets
Environment variables, gitignored `.env`, secret stores. **Never** commit API keys. Rotate if exposed.

### 5.5.4.3 Ethics of access
Respect provider terms; minimise personal data; aggregate sensitive locations before publication.

**Practice A3.** List what belongs in `.env.example` vs what must never be committed.

## Failure modes
Overwriting raw NetCDFs; undocumented API parameters; joining on unstable name strings; credentials in notebooks; analyses that cannot be rerun when a URL changes.
