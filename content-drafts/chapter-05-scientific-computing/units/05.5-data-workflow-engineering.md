## 5.5.1 End-to-end scientific workflows

### 5.5.1.1 Stages
1. **Acquire** — download/extract with logged parameters.  
2. **Validate** — schema, ranges, CRS, time zone, completeness.  
3. **Transform** — clean, join, aggregate; write interim products.  
4. **Analyse** — statistics/models on processed inputs only.  
5. **Publish** — tables/figures/package; never overwrite raw.

### 5.5.1.2 Idempotence
Re-running a stage with the same inputs yields the same outputs. Avoid “append forever” without deduplication keys.

### 5.5.1.3 Minimum manifest
```yaml
dataset_id: era5_t2m_multan_2015_2024
source: CDS ERA5 single levels
variable: 2m_temperature
units: K
spatial: "bbox [...]."
temporal: 2015-01-01/2024-12-31
access_date: 2026-03-15
licence: "Copernicus — verify current terms"
request: {product_type: reanalysis, ...}
checksum_sha256: "..."
notes: "Daily max on PKT local days"
```

## 5.5.2 SQL and structured data

### 5.5.2.1 Relational ideas
Separate **station metadata** from **observation time series**. Primary keys, foreign keys, one-to-many relationships.

### 5.5.2.2 Core SQL
`SELECT`, `WHERE`, `JOIN`, `GROUP BY`, `ORDER BY`; window functions at a working level. Always check counts before/after joins.

### 5.5.2.3 Tools
SQLite for local projects; PostgreSQL/PostGIS when multi-user or spatial SQL is needed (Subject 3). Pandas `read_sql` for analysis extracts.

**Practice A2.** Given tables `stations(id, name)` and `daily(station_id, date, tmax)`, write SQL for mean June tmax by station for one year; state how you would verify the result.

### Worked example — June mean maximum temperature by station

Use a half-open date interval: include 1 June and exclude 1 July. This avoids date-time boundary mistakes and makes the year explicit.

```sql
SELECT s.id, s.name, AVG(d.tmax) AS mean_june_tmax
FROM stations AS s
JOIN daily AS d ON d.station_id = s.id
WHERE d.date >= '2024-06-01'
  AND d.date <  '2024-07-01'
GROUP BY s.id, s.name
ORDER BY s.id;
```

For a deterministic teaching check, use this **synthetic-only** fixture:

```sql
CREATE TABLE stations (id INTEGER PRIMARY KEY, name TEXT NOT NULL);
CREATE TABLE daily (
  station_id INTEGER NOT NULL,
  date TEXT NOT NULL,
  tmax REAL,
  FOREIGN KEY (station_id) REFERENCES stations(id)
);

INSERT INTO stations VALUES (1, 'Station A'), (2, 'Station B');
INSERT INTO daily VALUES
  (1, '2024-06-01', 40.0),
  (1, '2024-06-02', 42.0),
  (1, '2024-06-03', 44.0),
  (1, '2024-07-01', 99.0),
  (2, '2024-06-01', 34.0),
  (2, '2024-06-02', 36.0);
```

Expected result:

| id | name | mean_june_tmax |
|---:|---|---:|
| 1 | Station A | 42.0 |
| 2 | Station B | 35.0 |

Reasoning: Station A's June mean is \((40 + 42 + 44)/3 = 42\); Station B's is \((34 + 36)/2 = 35\). The July value of 99 must not affect June. AVG ignores NULL values, so report the valid observation count as well if missing temperatures matter to interpretation.

**Verify before trusting the output:**

```sql
-- Expected: 5 rows in the June date window before joining to station metadata.
SELECT COUNT(*) AS june_rows
FROM daily
WHERE date >= '2024-06-01' AND date < '2024-07-01';

-- Expected: 0 rows. Any result indicates an orphan station key.
SELECT d.station_id, COUNT(*) AS n
FROM daily AS d
LEFT JOIN stations AS s ON s.id = d.station_id
WHERE s.id IS NULL
GROUP BY d.station_id;
```

The first check counts June observations independently of the join; the second checks referential integrity. If the analysis must retain stations with no June observations, use a LEFT JOIN with the date filter in the join condition, and decide explicitly how to represent a missing mean.

For a station with no June observations, compare these two choices. An `INNER JOIN` omits the station; a `LEFT JOIN` preserves it with a `NULL` mean and a valid-reading count of zero. Keep the date filters in the `ON` clause so the unmatched station is not removed by a `WHERE` predicate.

```sql
SELECT s.id, s.name, AVG(d.tmax) AS mean_june_tmax, COUNT(d.tmax) AS n_valid
FROM stations AS s
LEFT JOIN daily AS d
  ON d.station_id = s.id
 AND d.date >= '2024-06-01'
 AND d.date <  '2024-07-01'
GROUP BY s.id, s.name
ORDER BY s.id;
```

In the synthetic fixture, Station C has no observations: the inner-join query returns only Stations A and B; this left-join query returns Station C too, with `mean_june_tmax = NULL` and `n_valid = 0`. This is a deliberate reporting choice, not a zero-degree temperature.

### Guided practice

Change the query to return both the June mean and number of non-null tmax observations per station. Before running it, predict the output columns and row count. Then add a July observation and verify that the June result does not change.

**Guided feedback:** use COUNT(d.tmax) for non-null measurements; COUNT(*) counts joined rows. Keep the date predicate on the observation table and the grouping at one row per station.

### Independent practice

Using a fresh synthetic dataset for **June 2025**, write a query that returns each station's name, mean tmax, and number of non-null readings. Include one station with no June readings and state whether your chosen join should keep or omit it. Add one deliberately unmatched station_id; show the diagnostic query that detects it. Do not copy the worked example's data values.

### Assessment criteria (10 points)

- **3 points:** correct year-specific June interval; excludes July and other years.
- **2 points:** correct join key and one output row per intended station.
- **2 points:** correct mean and non-null count; handles missing values explicitly.
- **2 points:** reports independent row-count and unmatched-key checks.
- **1 point:** states the INNER JOIN versus LEFT JOIN consequence and labels all fixture data synthetic.

A response is not complete merely because the SQL executes: the learner must explain why the date bounds, join, aggregation, and validation checks answer the question.

## 5.5.3 APIs and acquisition

### 5.5.3.1 HTTP hygiene
Status codes, pagination, rate limits. Exponential backoff on 429/5xx.

### 5.5.3.2 Climate/EO endpoints
CDS, Earthdata, agency portals: pin client library versions; save the exact request payload; cite the dataset. Platform migrations break unpinned clients (Unit 2.5).

### 5.5.3.3 Local cache
Store downloads under `data/raw/` with manifest entries so analyses survive upstream path changes.

---

## 5.5.4 Provenance, licensing, credentials

### 5.5.4.1 Licence compliance
Attribution, share-alike, non-commercial clauses; derived-data rules. Do not redistribute restricted station data.

### 5.5.4.2 Secrets
Environment variables, gitignored `.env`, secret stores. **Never** commit API keys. Rotate if exposed.

### 5.5.4.3 Ethics of access
Respect provider terms; minimise personal data; aggregate sensitive locations before publication.

## Failure modes
Overwriting raw NetCDFs; undocumented API parameters; joining on unstable name strings; credentials in notebooks; analyses that cannot be rerun when a URL changes.
